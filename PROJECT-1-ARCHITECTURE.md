# Project 1 Architecture — Incident Update Polisher

**Project:** DevOps AI Assistant — Project 1  
**Capability:** LLM / Structured Generation  
**Status:** Ready for implementation  
**Depends on:** `ARCHITECTURE.md`

---

## 1. Goal

Build a small .NET web API that receives a rough technical incident note and turns it into a clear, professional status update for a selected audience.

Example input:

```json
{
  "incidentNote": "db slow, restarted pod, looks ok now",
  "audience": "leadership"
}
```

Example output:

```json
{
  "summary": "A database performance issue caused elevated latency. The affected pod was restarted and service performance returned to normal.",
  "impact": "Users experienced degraded performance during the incident.",
  "actionsTaken": [
    "Restarted the affected pod"
  ],
  "currentStatus": "Service performance is currently back to normal.",
  "nextSteps": [
    "Continue monitoring database performance"
  ]
}
```

The exact wording is generated by the AI; the **shape, validation, and rules are owned by the application**.

## 4. Component Responsibilities

### Domain

Contains only concepts and rules that are independent of HTTP, AI SDKs, databases, and infrastructure.

Example:

```csharp
public enum IncidentAudience
{
    Leadership,
    Customer
}
```

```csharp
public sealed record PolishedIncident(
    string Summary,
    string Impact,
    IReadOnlyList<string> ActionsTaken,
    string CurrentStatus,
    IReadOnlyList<string> NextSteps);
```

### Application

Owns the use case:

```text
Polish Incident
```

It coordinates:

```text
input
  -> validation
  -> audience selection
  -> prompt/context creation
  -> AI generation
  -> structured result validation
  -> result
```

### Infrastructure

Owns:

- `Microsoft.Extensions.AI`
- concrete AI provider configuration
- prompt file loading
- provider-specific translation
- external failures

### API

Owns:

- HTTP
- JSON serialization
- endpoint mapping
- HTTP status codes
- OpenAPI
- exception handling

## 8. Input Contract

```csharp
public sealed record PolishIncidentRequest(
    string IncidentNote,
    IncidentAudience Audience);
```

### Validation

`IncidentNote`:

- required
- trim whitespace
- reject empty values
- enforce a configurable maximum length

`Audience`:

- required
- only supported enum values
- reject unknown values

Example deterministic error:

```json
{
  "code": "INVALID_INCIDENT_NOTE",
  "message": "IncidentNote is required."
}
```

---

## 9. Output Contract

The AI should return a structured object equivalent to:

```json
{
  "summary": "string",
  "impact": "string",
  "actionsTaken": ["string"],
  "currentStatus": "string",
  "nextSteps": ["string"]
}
```

### Output rules

- all top-level fields are required
- arrays may be empty
- no invented facts
- no unsupported claims
- no markdown required in the API contract
- max lengths should be validated after generation
- malformed AI output is an application error, not silently accepted

## 10. Prompt Design

### System prompt

Responsibilities:

- define the role
- define factuality rules
- prohibit invention
- define the audience behavior
- define expected structured output
- define tone

Example content:

```text
You are a DevOps incident communication assistant.

Transform technical incident notes into concise and professional
status updates.

Rules:
- Never invent facts.
- Do not claim an incident is resolved unless the input supports it.
- Do not add metrics, root causes, timelines, or impact that were not provided.
- Preserve uncertainty when the input is uncertain.
- Keep language appropriate for the requested audience.
```

### Leadership prompt

Focus:

- business impact
- current status
- actions taken
- next steps
- concise communication

### Customer prompt

Focus:

- customer-visible impact
- plain language
- avoid internal jargon
- avoid exposing unnecessary internal infrastructure details
- no blame
- no unsupported root-cause claims

Store prompt text in files, not large string literals inside C#.

## 11. Prompt Pipeline

The application should construct AI input deterministically:

```text
request
  |
  +--> validate
  |
  +--> select audience
  |
  +--> load system prompt
  |
  +--> load audience prompt
  |
  +--> construct user message
  |
  v
AI generator
```

Keep prompt construction separate from the provider adapter.

## 14. Error Model

Map expected failures to application-level errors.

Suggested codes:

```text
INVALID_REQUEST
INVALID_AUDIENCE
AI_PROVIDER_UNAVAILABLE
AI_RESPONSE_INVALID
AI_REQUEST_FAILED
```

Example:

```json
{
  "code": "AI_RESPONSE_INVALID",
  "message": "The AI provider returned an invalid response format.",
  "traceId": "..."
}
```

Never expose:

- raw provider response
- API key
- stack trace
- internal exception details

## 15. Testing Plan

### Unit tests — IncidentPolisher

Test:

1. leadership uses leadership prompt
2. customer uses customer prompt
3. empty incident note is rejected
4. unsupported audience is rejected
5. AI is not called for invalid input
6. valid AI result is mapped correctly
7. malformed AI output is rejected
8. cancellation token is propagated
9. provider failures become expected application errors

### Integration tests

Test:

1. `POST /api/incidents/polish` with valid request returns `200`
2. invalid request returns `400`
3. malformed AI response returns the expected server/application error
4. response JSON matches the public contract

Use a deterministic fake AI provider for tests.

Do not test whether the LLM chooses a specific sentence.
